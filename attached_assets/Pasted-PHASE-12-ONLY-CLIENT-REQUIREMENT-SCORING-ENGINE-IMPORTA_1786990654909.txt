PHASE 12 OBJECTIVE

Build a configurable, explainable scoring system for:

A. ClientScore
B. RequirementScore

The scoring engine must be configuration-driven and must NOT contain hardcoded business scoring rules inside the service.

The system must explain:
- why the score is high/low
- which factors contributed positively
- which factors contributed negatively
- which factors were unavailable because their values are UNKNOWN
- which configuration version produced the score

==================================================
1. CORE PRINCIPLE
==================================================

Scoring must never treat UNKNOWN as NO.

Example:

Parking = UNKNOWN

This must NOT reduce the score as:

Parking = No

UNKNOWN simply means:
"not enough information yet."

The scoring engine must distinguish:

KNOWN
UNKNOWN
NOT_APPLICABLE

Only KNOWN values should normally participate in scoring unless a scoring rule explicitly says otherwise.

==================================================
2. REQUIREMENT SCORE
==================================================

Implement:

calculateRequirementScore(requirement)

The calculator must consume the existing Requirement record and:

1. Read Requirement.Fields.
2. Read DependencyEngine relevance state where appropriate.
3. Read ScoringConfig.
4. Evaluate only applicable scoring factors.
5. Ignore UNKNOWN fields unless configuration explicitly defines another behavior.
6. Produce an explainable result.

Required result structure:

{
  score: number,
  band: string,
  factors: [
    {
      factorId,
      field,
      label,
      value,
      contribution,
      reason,
      state
    }
  ],
  positiveContributions: [],
  negativeContributions: [],
  unknownFactors: [],
  calculationVersion,
  calculatedAt
}

Do not expose internal implementation details unnecessarily through the UI/API.

==================================================
3. CLIENT SCORE
==================================================

Implement:

calculateClientScore(lead)

Client scoring must be based only on configured factors.

Possible configured factors may include:

- number of active transactions
- number of active requirements
- requirement completeness
- response/activity signals
- follow-up responsiveness where existing data supports it
- client tags
- transaction activity
- deal history where existing data supports it

DO NOT invent unavailable data.

If an input is unavailable:

state = UNKNOWN

and it should not automatically reduce the score.

==================================================
5. SCORE BANDS
==================================================

Score bands must also be configuration-driven.

Example:

0–29   = Cold
30–49  = Warm
50–69  = Good
70–84  = Hot
85–100 = Very Hot

BUT:

Do not assume these exact values are mandatory.

Inspect the existing ScoringConfig first.

If the current system already defines bands, preserve them.

If missing, create sensible defaults in configuration.

The service must resolve the band from configuration rather than hardcoding it.

==================================================
6. NORMALIZATION
==================================================

The final score must have a predictable range.

Prefer:

0–100

If weighted factors are used:

normalizedScore =
  weightedContribution / maximumApplicableContribution * 100

UNKNOWN factors must not artificially lower the normalized score.

Example:

10 scoring factors exist.

Only 4 are KNOWN.

Score must be calculated against the applicable 4, not automatically against all 10.

==================================================
7. EXPLAINABILITY
==================================================

Every score calculation must be explainable.

Example:

+20

+20
"Preferred location is specified."

BHK:
+15
"Target BHK is specified."

Urgency:
+10
"Client has an active timeline."

Possession:
+7
"Possession preference is specified."

Parking:
UNKNOWN
"No score contribution because parking preference is not known."

Do not create fake explanations.

Reasons should come from configuration where practical.

Historical score results must not become impossible to interpret after configuration changes.

Do NOT rewrite historical Requirement fields just because scoring configuration changes.

==================================================
18. IMPORTANT — DO NOT CONFUSE SCORE WITH COMPLETENESS
==================================================

RequirementScore is NOT:

"How many fields are filled?"

Completeness is a separate concept.

A Requirement can be:

Score = 85
Completeness = 40%

because the known information may strongly indicate a serious requirement.

Likewise:

Completeness = 90%
Score = 30

is possible if configured business signals indicate a weak/low-priority requirement.

Do not merge these concepts.
