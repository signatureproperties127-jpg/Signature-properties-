====================================================
CORE OBJECTIVE
====================================================

Build a configuration-driven Dependency Engine that determines:

VISIBLE
HIDDEN
RELEVANT
NOT_RELEVANT

for Requirement questions/fields based on:

TransactionType
Category
SubCategory
and previously known Requirement values.

The Dependency Engine controls which questions are relevant to the current client requirement.

It does NOT decide whether a Requirement is valid.

UNKNOWN remains a valid state.

CLIENT

Example:

SubCategory = Flat

Dependency Engine may determine:

TenantType → RELEVANT
MoveInDate → RELEVANT

====================================================
IMPORTANT DISTINCTION
====================================================

FieldConfig answers:

"What fields exist?"

FormRegistry answers:

"Which configuration applies to this Transaction + Category + SubCategory?"

DependencyConfig answers:

"Under the current answers/context, which fields are relevant?"

These three layers MUST remain separate.

====================================================
THREE-STATE REQUIREMENT MODEL
====================================================

Do NOT confuse dependency state with Requirement field state.

Requirement field state:

UNKNOWN
KNOWN
NOT_APPLICABLE

Dependency state:

VISIBLE
HIDDEN
RELEVANT
NOT_RELEVANT

Example:

Parking field:

Dependency:
RELEVANT

Requirement:
UNKNOWN

This means:

"The system wants to know Parking, but the client has not told us yet."

Another example:

SwimmingPool for a particular requirement:

Dependency:
NOT_RELEVANT

Do not ask the client about it.

====================================================
MULTIPLE RULES
====================================================

The engine must define deterministic behavior when multiple rules target the same field.

Do NOT rely on object iteration order.

Implement explicit precedence.

Recommended precedence:

1. NOT_RELEVANT
2. HIDDEN
3. RELEVANT
4. VISIBLE

If the existing architecture has a stronger precedence model, document and use it consistently.

The final result for every target field must be deterministic.

====================================================
CONTEXT RESOLUTION
====================================================

The engine receives a context object such as:

{
  transactionType: "Rent",
  category: "Residential",
  subCategory: "Flat",
  fields: {
    BHKMin: {
      state: "KNOWN",
      value: 2
    },
    TenantType: {
      state: "UNKNOWN"
    }
  }
}

The engine must NEVER assume an UNKNOWN value means:

false
0
"No"
"None"

UNKNOWN means:

"The answer is not known yet."

Therefore a rule:

TenantType == Family

must NOT execute as true when TenantType is UNKNOWN.

====================================================
FIELD STATE INTERACTION
====================================================

If a source field is:

UNKNOWN

rules depending on that source cannot incorrectly force a positive result.

Example:

Parking = UNKNOWN

Rule:

Parking == "2"

must not evaluate as true.

Return the appropriate unresolved/default dependency state.

Document this behavior.

====================================================
DEFAULT BEHAVIOR
====================================================

Every configured field must have a deterministic default state.

Recommended:

- If field belongs to resolved FormConfig and no dependency excludes it → RELEVANT/VISIBLE according to configuration.
- If field is outside the current form context → NOT_RELEVANT.
- If dependency conditions hide it → HIDDEN.
- If dependency explicitly marks it irrelevant → NOT_RELEVANT.

Do not leave fields in an undefined state.

API
====================================================

Add APIs consistent with existing V2 routing.

At minimum:

GET /api/v2/dependencies

GET /api/v2/dependencies/evaluate

Example:

GET /api/v2/dependencies/evaluate?
transactionType=Rent&
category=Residential&
subCategory=Flat&

If requirementId is supplied:

- load Requirement
- load its Transaction
- resolve FormConfig
- evaluate dependencies
- return final field states

====================================================
SERVER-SIDE VALIDATION
====================================================

Dependency Engine is primarily about relevance/visibility.

It must NOT weaken Phase 7 validation.

Phase 7 rules remain:

- absent fields are valid
- UNKNOWN is valid
- provided invalid values are rejected
- numeric/range validation remains
- FormVersion remains immutable
- LeadID/TransactionID relationships remain immutable

Do not make a field mandatory merely because it is RELEVANT.

RELEVANT means:

"This is useful to ask/capture."

It does NOT mean:

"This must already have a value."
