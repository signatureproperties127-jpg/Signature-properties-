PHASE 15 ONLY — CLIENT LIST / QUERY VIEW

PHASE 1–14 ARE COMPLETED.
Do NOT repeat or redesign completed phases.
Do NOT start Phase 16.

OBJECTIVE

Redesign the Client List so the agent works with CLIENTS,
not with a confusing Lead/Requirement database screen.

Core model remains:

ONE CLIENT = ONE LEAD

CLIENT
 └── TRANSACTIONS
      └── REQUIREMENTS / NEEDS

Requirements are living Needs and can be used as a
query/filter/view layer, but must NOT become a separate
primary client entity.

==================================================
1. CLIENTS — NOT LEADS
==================================================

The primary navigation label must be:

CLIENTS

Not:

Leads

Where the UI is user-facing, replace "Lead" terminology with
"Client" unless the technical/API field name must remain LeadID.

Technical compatibility may continue using:

LeadID

But UI language should use:

Client
Client ID
Client Status
Client Lifecycle
Client Needs

==================================================
2. CLIENT LIST DESIGN

Create a clean agent-first client table/list.

Default columns:

- Client
- Mobile
- Active Needs
- Primary Need
- Budget
- Location
- Client Status
- Client Lifecycle
- Client Score
- Last Contact
- Next Follow-up
- Assigned Agent

==================================================
6. REQUIREMENT QUERY IS NOT A NEW ENTITY
==================================================

Do NOT create:

"Requirement Client"

"Requirement Customer"

or another Lead/Client record.

The query works through:

Client
→ Transaction
→ Requirement

and returns the parent Client.

One client may appear only once in the result even if multiple
Requirements match.

Example:

Rahul has:

Requirement R001
3 BHK Vesu

Requirement R002
4 BHK Vesu

Both match.

Result:

Rahul Shah

NOT:

Rahul Shah
Rahul Shah

Deduplicate by LeadID.

==================================================
