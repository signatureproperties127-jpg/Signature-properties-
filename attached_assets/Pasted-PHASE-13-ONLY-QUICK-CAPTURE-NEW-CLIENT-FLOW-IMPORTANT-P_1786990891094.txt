==================================================
2. BUSINESS MODEL — NON-NEGOTIABLE
==================================================

The business model is:

ONE CLIENT = ONE LEAD

A Client/Lead can have:

ONE OR MANY TRANSACTIONS

A Transaction can have:

ONE OR MANY REQUIREMENTS

Therefore:

CLIENT
  ↓
LEAD
  ↓
TRANSACTION
  ↓
REQUIREMENT

Do NOT create another Client entity.

Do NOT create another Lead for every requirement.

Do NOT create a separate Requirement-only client record.

==================================================
3. QUICK CAPTURE PURPOSE
==================================================

The current "Add Client" form is too large and creates only a Lead.

Replace/adapt it into a SMALL Quick Capture flow.

The agent should be able to save a new client in approximately one short interaction.

The first capture is NOT supposed to collect the complete requirement.

The first capture only records what the agent knows at that moment.

Everything else remains UNKNOWN.

==================================================
10. ATOMIC CREATION
==================================================

THIS IS THE MOST IMPORTANT PART.

One Quick Capture save must create:

Lead
+
Transaction
+
Requirement

as ONE logical operation.

Flow:

Quick Capture
   ↓
Duplicate Check
   ↓
Existing Lead?
   ├─ YES → use existing Lead
   └─ NO  → create Lead
   ↓
Create Transaction under Lead
   ↓
Create Requirement under Transaction
   ↓
Populate only supplied initial fields
   ↓
Everything else = UNKNOWN
   ↓
Calculate scores
   ↓
Return Client Workspace reference

Do NOT create a Requirement without a Transaction.

Do NOT create a Transaction without a Lead.

==================================================
13. ATOMICITY / ROLLBACK
==================================================

The Quick Capture operation must behave atomically.

If:

Lead created
Transaction creation fails

the system must not leave a partially-created Lead if the repository supports rollback.

If:

Lead + Transaction created
Requirement creation fails

the system must not leave an incomplete Quick Capture transaction.

Implement this using the repository's existing safe write/transaction pattern.

If true database transactions are not available because the system uses JSON:

implement a safe snapshot/rollback mechanism at the repository/service boundary.

Do NOT claim atomicity if the implementation cannot guarantee it.

Write tests specifically for partial failure.
