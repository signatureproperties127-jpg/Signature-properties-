PHASE 14 ONLY — CLIENT WORKSPACE / NEEDS-FIRST UI

Phase 1–13 are already completed and passed their respective gates.
Do NOT repeat, redesign, or rewrite completed phases.
Do NOT start Phase 15.

OBJECTIVE

Replace the current tab-centric Client Workspace with a
NEEDS-FIRST, conversation-driven Client Workspace.

The fundamental model remains:

CLIENT/LEAD
   ↓
TRANSACTION
   ↓
REQUIREMENT / NEED
   ↓
MATCHING → SITE VISIT → NEGOTIATION → TOKEN → DEAL

One Lead = one client.
One Lead can have multiple Transactions.
One Transaction can have multiple Requirements.

A Requirement is a living client need.
UNKNOWN is valid.
Do not force agents to complete forms.

IMPORTANT:
The UI must behave like an agent's memory/workspace, NOT like a data-entry form.

==================================================
5. KNOWN VS TO DISCOVER
==================================================

Inside each Need Card provide:

KNOWN

✓ Budget: ₹80L–₹1.20Cr
✓ Location: Vesu
✓ BHK: 3
✓ Property Type: Flat

TO DISCOVER

? Possession
? Urgency
? Furnishing
? Parking

Do NOT interpret UNKNOWN as NO.

UNKNOWN means:

"We have not asked / captured this yet."

NOT_APPLICABLE means:

"This field does not apply to this requirement."

KNOWN means:

"We have an actual captured value."

6. NEXT QUESTIONS
==================================================

Use the existing:

V2NextQuestionService

API:

GET /api/v2/requirements/:requirementId/next-questions

Display the top 1–3 questions.

Example:

NEXT QUESTIONS

1. "Possession kab chahiye?"
2. "Kitne parking chahiye?"
3. "Fully furnished chahiye ya semi-furnished?"

Each question should have:

[Ask]

After the agent gets the answer:

[Save Answer]

The answer must PATCH the SAME RequirementID.

Do NOT create a new Requirement.

Example:

Before:

Possession = UNKNOWN

After:

Possession = "0-6 Months"

Same:

RequirementID = R000123
